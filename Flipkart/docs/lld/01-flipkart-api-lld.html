04

Bootstrap & Redis Resilience Shipped

Bug: with no reconnectStrategy, node-redis's default never gives up on a failed connection — so await redisClient.connect() at boot hung forever whenever Redis was down, and app.listen() never ran. Fix has two parts: boot is bounded by a timeout so it never waits on Redis, and every runtime call goes through one gatekeeper that fails fast to Mongo instead of throwing or hanging.

4.4 Decisions

A timeout, not a "give up" strategy

reconnectStrategy itself never gives up — it always returns a delay, never Error or false. The thing that's bounded is boot's wait (Promise.race with 3s), which is a completely separate concern from whether Redis keeps trying to come back.

disableOfflineQueue avoids a replay storm

node-redis's default queues commands while disconnected and fires them all at once on reconnect — a self-inflicted spike right when Redis is fragile after coming back. Rejecting immediately instead means the gatekeeper's isReady check is the only fallback path, and it's always accurate.

/ready never gates on Redis

If readiness depended on Redis, an outage would make every pod "not ready" at once and an orchestrator would kill them all simultaneously — the opposite of "never unavailable because Redis is down". Redis state is exposed in the JSON for humans/dashboards, not enforced for traffic routing.

One gateway, no scattered try/catch

session.ts used to wrap every Redis call in its own try/catch with a logged fallback. That's now centralized in redisGateway.ts — feature code never imports redisClient directly, it calls cacheGet/cacheSet/cacheDel and gets a fail-safe result for free.

No circuit-breaker library — yet

isReady + a per-call timeout already covers "Redis down" and "Redis up but slow" for a single instance. A library (bulkhead, sampling-window trip thresholds) earns its cost once there's real multi-tenant load and noisy-neighbor traffic to isolate — not before.

07

Sequence Flows — Add to Cart vs. Add to Wishlist

Both are a POST .../ that must not duplicate a line for the same product — but they get there differently. Cart has a number to accumulate (qty), so a single atomic upsert handles "new" and "already there" in one DB call. Wishlist has no number to accumulate — it's a pure yes/no — so it writes and lets the unique index reject the duplicate.

08

Cursor Pagination

Every list endpoint sorts by _id ascending — a MongoDB ObjectId is monotonically increasing, so it's a stable, index-friendly cursor for free.

10.3 Cart & Wishlist — userId scoping + atomic quantity

CollectionBeforeAfter (shipped)
CartItemunique { productId } — one shared cart, global+ userId (required) · unique { userId, productId }
WishlistItemunique { productId } — one shared wishlist, global+ userId (required) · unique { userId, productId }
  • Add (POST /cart) becomes one atomic call: findOneAndUpdate({userId,productId}, {$inc:{qty}}, {upsert:true}) — replaces the current findOne-then-save/create dance, and removes its lost-update race under concurrent requests.
  • New — PATCH /cart/:id/quantity { delta }, one endpoint for both directions (kept single, as agreed):
    • delta > 0 → findOneAndUpdate({_id,userId}, {$inc:{qty:delta}})
    • delta < 0 → guarded: findOneAndUpdate({_id,userId,qty:{$gt:-delta}}, {$inc:{qty:delta}}) — qty can never go negative in the DB
    • guarded update returns null (qty ≤ decrement amount) → line is removed entirely via findOneAndDelete
    • no Mongo transaction needed — a single-document $inc is already atomic, so concurrent decrements can't corrupt qty
  • PUT /cart/:id (absolute set) and DELETE /cart/:id stay as-is, just scoped by userId now.

10.6 Decisions

One jti, both tokens

Access and refresh share a session id. Revoking it kills both at once — no separate ledger for each token type.

Revocable access token — a real trade-off

Every request now pays for a session lookup, not just signature verification — the usual "stateless JWT, no DB hit" benefit is given up on purpose, because a 6h access token needs to die on logout, not just expire.

Redis-first, Mongo-fallback, self-healing

Redis errors don't fail the request — they fall through to Mongo, and a Mongo hit gets written back into Redis so the next request is fast again. Session code itself no longer contains any try/catch for this — it calls cacheGet/cacheSet/cacheDel and the fallback is baked into those. Full resilience mechanics in §04.

No new dependency for jti

crypto.randomUUID() is Node stdlib (available since the project's engines.node >=20) — no uuid package.

TTL index over a cleanup cron

Mongo expires stale Session docs on its own; Redis keys carry their own EX. Neither store needs a scheduled sweep.

Self-deactivate via PUT /users/me

No admin/roles system exists, so isActive:false is reachable only by the user on themselves, through the existing profile-update route — not a new endpoint. Re-activation is out of scope.

No refresh-token rotation — yet

Each refresh reuses the same jti rather than rotating to a new one. Rotation adds theft-detection (reusing an old refresh token signals a stolen one) but needs a token-family chain — skipped for now, add when it's actually needed.

11

Design Decisions

Deliberate simplifications, not gaps — what each one costs, and when it'd need revisiting.

No service layer

Controllers call Mongoose models directly. Three features, no cross-model business rules complex enough to earn an extra layer — one would be an interface written for a single implementation.

Cart dedupes by incrementing

Unique index on productId + an app-side findOne-then-branch keeps "one line per product" true without a compound key.

"ek product ki ek hi cart line — dobara add hone pe qty badhti hai"

→ superseded — see §10: findOne-then-save had a lost-update race under concurrent requests, replaced with an atomic $inc upsert

Wishlist dedupes by DB index, not a pre-check

No findOne before insert — write, then catch Mongo's duplicate-key error (code 11000) as 409. One round trip instead of two, and race-safe: two parallel adds can't both slip through a check-then-insert gap.

Cursor pagination, not offset

ObjectId is monotonic, so { _id: { $gt: cursor } } is a stable, index-friendly sort key. Offset pagination degrades with depth — the seeder targets up to 1 crore products, where that matters.

No auth, no userId

Cart and Wishlist are single global collections. Fine at learning-project scope; multi-tenant would need a userId partition key plus auth middleware everywhere.

→ superseded — see §10: the Users module now adds auth + mandatory userId scoping on both collections

Redis is a gatekeeper-guarded cache, never a hard dependency

Superseded the earlier "Redis connects, nothing uses it" note once Users/Auth (§10) put it to work. Full resilience mechanics — boot sequence, runtime gatekeeper, config, decisions — now live in their own section, §04.

res.headersSent guard in errorHandler

requestTimeout can end a response while a slow query is still running — writing headers again would throw ERR_HTTP_HEADERS_SENT, so that case delegates to Express's own final handler instead.

CastError auto-maps to 400

A malformed :id is a client mistake, not a server fault. Without this branch it falls through to the generic 500 path and gets logged as if it were a real bug.

Seeder bypasses Mongoose hydration

Bulk-inserts via the raw MongoDB driver and drops non-_id indexes before the insert, rebuilding after. At millions-of-docs scale, document hydration and live index maintenance are the dominant costs.
